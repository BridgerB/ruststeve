- **Runs without an event row:** the 18 `6b-head` trials. The HEAD binary predates the event log, so they were backfilled from gym.db by id, A rows only, selected by region.
- **The attempts log itself:** 118 unparseable lines (0.44%). Several bot processes append to one file without a lock, so two rows sometimes merge into one line. Every script I used skips them.
- **Harness faults:**
  1. **Server B crashed once** (11:21:33 UTC, a 60 s tick). My unniced cargo build starved the 2-CPU box during six staggered arrivals. Builds are niced (`nice -n 19 … -j 1`) since.

  3. **Region confound**, as in section 5.
  4. **False "ghost cap" flags (6c+lsm14/15).** My check required a block to leave the inventory, but the SDK never decrements the held stack on placement, so real caps were flagged as ghosts. Server truth showed cobblestone in the flagged cells. 6c+lsm15's batch was corrupted and stopped.

  6. **A crystals trial spawned in a bed crater**: invalid, fixed with a crater refill.
  7. **The crystals step hot-looped 171× on one unreachable crystal**: fixed by persisting give-ups.

## 11. What I would tell the other bot's agent (steve)

These are bugs or designs it likely shares, because ruststeve's SDK is a port of typecraft. `src/path/movements.rs` says so in its header.

1. **Diagonal moves have no lava rule.** In ruststeve, `move_diagonal` checked neither the destination's neighbours nor the two corner cells the 0.6-wide body sweeps, while straight walks refuse lava-adjacent cells. A diagonal past a lava-floored corner killed rust-gym-003 (6c+lsm10). typecraft's movements are the source of this code.
2. **Relative entity moves read the wrong field names.** The packet schema says `dX/dY/dZ`; the code read `dx`, so every relative move was applied as 0. Mobs, including the dragon, were frozen between absolute syncs. Worth a grep in typecraft's entity handler.
3. **The client's placement prediction isn't server truth.** A placed block is predicted locally at once. Anything that re-reads the cell a few ticks later counts rejected placements as placed. Judge by the cell after ~8 ticks, when a rejection's revert has arrived.
4. **The held stack isn't decremented on placement.** Vanilla predicts this client-side and the server doesn't confirm a success. Inventory counts after placing are stale.
5. **The path follower sprints toward every waypoint.** Near lava edges the momentum carried ruststeve bots off; it now doesn't sprint within 1 block of lava and re-checks the waypoint's cells live.
6. **Shared box:** a plain release build on the 2-CPU box can push Server B past its 60 s tick watchdog. Build with `nice -n 19 … -j 1` while anything runs.
7. **Dragon facts, if steve reaches the End:**
   - beds placed under or near a sitting dragon's head and neck are destroyed by its parts, so place and use in the same tick;
   - a `/summon`ed dragon needs `DragonPhase:0` to perch;
   - the dragon destroys cobble pillars, so use obsidian.

## 12. The learning system, what was hard, and what I need decided

**What it made easier.**
- `compare.ts` ended arguments: four verdicts, each from a rule, not my opinion.
- Per-build summaries from `attempts.jsonl` made the decisive diagnosis possible. The drop/scoop counts per bot found the regression in minutes.
- Primitive rows showed where `lava_safe_move` vetoes, in the thousands of rows.
- The server-side pass checks (dragon, crystals) never lied once, while the bot's own view did, repeatedly (ghost beds, frozen positions).

**What it made harder.**
- Unpaired baselines: a backfilled baseline from another world decided three comparisons before I noticed.
- The append log interleaves under concurrent writers.
- Clause (a) plus fast iteration meant 16 builds in one chain and 111 unmeasured trials. Comparisons rarely completed on one build.

**What I would not do again.**
- Delete a step on the strength of one death: "drop to scoop level", which cost every comparison from 6c+lsm10 to lsm14.
- Change movement behaviour (the 1.6 stop-short) without re-running the drill.
- Compare against a backfilled baseline.
- Build unniced on the shared box.
- Ship a check that depends on a client-side value I hadn't verified against the server: the held-stack count.

**Decisions I need from the strategist.**
1. **The portal build for the next race:** 6b-head (50% clean but 0.83 deaths per trial) or 6c+lsm16 (11% clean, 0.12 deaths per trial)? Or a 6b-based build with only the safety fixes that don't change progress: diagonal lava rule, live lava check, no sprint near lava, verified caps, no-pickaxe abort. That last one is my recommendation, measured as concurrent arms from its first batch.
2. **Clause (a) under concurrent arms:** keep stopping a B batch on any changed-path death, or run to the cap and let compare.ts decide on deaths too?
3. **Kit:** a 4th iron pickaxe, or a mid-task craft, for the portal (both arms run out). And is a 16-bed dragon kit acceptable for the race plan, given ~15–19 damage per bed?
4. **Crystals:** keep the bow approach (6/10 at best), or move to the doc's climb-the-tower approach for the caged and tall towers?
5. **The append log:** switch the gym/race event log to per-process files, or to SQLite only?
